## 1. 为什么需要这份文档

赛题把"敏感信息保护"列为**实现约束**（即合规要求，非加分项）。而本平台的采集面天然会接触到敏感数据：

| 数据来源 | 可能携带的敏感信息 |
|---|---|
| 容器环境变量 | API Key、数据库密码、Token、第三方凭据 |
| 进程命令行（`cmdline`） | `--password=...`、`--token=...`、内网地址 |
| 业务日志 | 用户身份、手机号、身份证、会话 ID、请求体 |
| Agent 任务轨迹 | 工具调用参数、用户输入、外部服务凭据 |
| 配置 / 部署 | ZSvirt 凭据、数据库连接串、局域网地址 |
| 事件原始载荷 `Event.raw` | 上述全部（因为它是原样保存的） |

**B 侧的定位**：B 是数据的**汇聚点**，也是最容易把敏感信息扩散到 API 与前端的一环。因此脱敏的第一道有效关口在 B 的 `normalize` 模块（A 的探针侧做不做脱敏是 A 的决定，但 B **不得假设 A 已经脱敏**）。

---

## 2. 三层防护

```
A 探针（可选前置脱敏）
      │  上报
      ▼
B: ingest  ──▶  normalize（★ 主要关口：字段过滤 + 脱敏）──▶ events / graph
                                                              │
                                                              ▼
                                             B: api ──▶ C 前端（不返回敏感字段）
```

| 层 | 责任方 | 措施 |
|---|---|---|
| 采集层 | 成员 A | 可选：探针侧不采集明显敏感字段（如跳过环境变量） |
| **汇聚层** | **成员 B** | **强制**：字段过滤 + 脱敏管道；`Event.raw` 入库前必过 |
| 展示层 | 成员 C | 不渲染敏感字段；不在前端日志打印完整响应体 |

## 3. 字段过滤规则（丢弃而非脱敏）

以下内容**直接丢弃，不入库**：

| 目标 | 匹配方式 |
|---|---|
| 环境变量类字段 | 键名匹配 `*_KEY`、`*_TOKEN`、`*_SECRET`、`*_PASSWORD`、`*_PASSWD`、`*_CREDENTIAL`、`AWS_*`、`OPENAI_*` |
| 凭据 / 证书 | 键名匹配 `authorization`、`cookie`、`set-cookie`、`private_key`、`certificate` |
| 连接串 | 值匹配 `://[^:]+:[^@]+@`（含用户名密码的 URL） |
| 已知的密钥形态 | 值匹配长随机串启发式规则（如 `sk-`、`ghp_`、`AKIA` 前缀） |

> **默认策略**：**白名单优先**。`attributes` 只接受契约中显式声明的字段，未声明字段默认丢弃，而不是默认保留。

## 4. 脱敏规则（保留但掩码）

对确实有诊断价值、但可能含敏感信息的字段，保留字段本身、掩码其内容：

| 字段 | 处理 | 示例 |
|---|---|---|
| `process.cmdline` | 参数值掩码，保留参数名与命令 | `python serve.py --api-key=*** --port 8000` |
| `Event.message` | 命中规则时掩码匹配片段 | `connect failed to db://user:***@10.x.x.x:5432` |
| `Event.raw` | **整体走脱敏管道**；无法安全脱敏的键直接删除 | — |
| IP 地址 | 【待确认】是否掩码内网地址；建议**保留**（拓扑关联需要） | — |
| `labels` / `annotations` | 按 §3 规则过滤键名 | — |
| 身份标识（用户 ID / 手机号） | 哈希化（单向），保留可关联性、去除可读性 | `user_7f3a9c` |

**掩码实现要点**：
1. 脱敏必须**幂等**（重复执行结果一致）。
2. 脱敏必须**可审计**：记录"某字段被脱敏"的标记，但不记录原文。
3. 脱敏后的事件仍须满足 `DATA_MODEL.md` 的字段契约（不得因脱敏导致必填字段缺失）。

## 6. 红线（违反即视为缺陷）

1. **禁止**把未脱敏的凭据写入数据库、日志、API 响应或 `Event.raw`。
2. **禁止**把真实 token / 密码 / 密钥 / 证书提交到仓库（`.gitignore` 已覆盖，但提交前仍需人工复核）。
3. **禁止**把局域网地址、个人机器路径写进产品源码或文档。
4. **禁止**在诊断证据（`Diagnosis.evidence`）中回显敏感字段原文。
5. **禁止**在演示录屏中出现真实凭据或内网拓扑细节。

## 8. 实现对照：A 侧探针 vs B 侧兜底

> 本节是 2026-09-17 契约冻结后新增的。成员 A 已实现探针侧第一道过滤
> （`agents/probe/sensitive.py`），B 侧兜底实现为 `backend/app/normalize/sensitive.py`。
> 两者**必须一致**，但有 **2 处刻意差异**需要有据可查。

### 8.1 共享测试向量（一致性的唯一依据）

| 项 | 值 |
|---|---|
| 向量文件 | [`shared/sensitive_vectors.json`](../shared/sensitive_vectors.json) |
| B 侧校验 | [`backend/tests/test_sensitive_vectors.py`](../backend/tests/test_sensitive_vectors.py) |
| 向量条数 | 31（键名 21 + cmdline 13 + 过滤 9，含 **10 条反例**） |
| 文件编码 | **纯 ASCII**（刻意如此 —— 零依赖的探针要能不靠 JSON 库读取） |
| 行格式 | `CASE <id> <expected> <JSON input>` |

**为什么要向量而不是"口头对齐"**：两侧规则靠注释约定必然漂移。向量把
"行为一致"变成可执行断言 —— 任何一侧改动导致不一致，测试立刻失败。

**反例同样重要**：只有正例时，"一致"可能只是"都错"。向量含 10 条反例
（`keyboard` / `key` / `region` / `tokenizer` / `secretary` / `password_hint` 等），
用于防止误杀导致诊断信息丢失。

### 8.2 两处刻意差异（B 侧更严）

| # | 差异 | 探针（A） | 兜底（B） | 为什么 B 更严 |
|---|---|---|---|---|
| 1 | **裸字段名** | 只认 `_PASSWORD` 后缀 → `{"password": "x"}` **漏过** | 额外全等匹配 `password` / `passwd` / `secret` / `token` / `api_key` | `{"password": "x"}` 是最常见的现场形态。B 是兜底关口，不能跟着漏。用**全等**而非子串，故 `password_hint` / `secretary` / `tokenizer` 不会被误杀 |
| 2 | **递归深度** | `filter_sensitive` 只处理 **dict 第一层**，不递归 | 对 **dict 与 list 都递归** | 凭据藏在数组元素里是真实泄漏路径（如 Docker inspect 的 `Env` 数组）。同样地，B 不能跟着漏 |

两处差异都已由向量覆盖（`k30`–`k35`、`f03`–`f05`、`f07`、`f09`），
因此**不会被误认为实现漂移**。

> **建议（不阻塞）**：探针侧若愿意，可把这两条规则补齐，让两侧完全等价。
> 这属成员 A 的模块，B 不越界修改；若 A 决定对齐，向量无需改动
> （向量的期望值已是更严的那一侧）。

### 8.3 已知折中（接受，不修）

| 项 | 表现 | 判断 |
|---|---|---|
| `cookie_count` | 因含子串 `cookie` 被判敏感（两侧一致） | 接受。过度脱敏只损失一点诊断信息；规则不一致会形成真实缝隙，风险更高 |
| `--tokenizer bpe` | 因含子串 `token` 被误掩码（两侧一致） | 接受。理由同上。若将来要精确化，须**两侧同时**改并把向量一起更新 |

### 8.4 与 A 的 `process` sourceId 规则的交叉约束

A 确认 `process` 的 `sourceId` 为 `starttime + pid`（`API_CONTRACT.md` §3.3.1）。
这带来一个**跨契约约束**：

> 资源 ID 采用 `{kind}:{source}:{sourceId}`，且探针 ID 为
> `{kind}:probe:{agentId}:{sourceId}` —— **共四段**。
> 因此 `starttime` 与 `pid` 之间**必须用 `.` 连接**（如 `12345.678`），
> **不能用 `:`**，否则 ID 会变成五段、无法解析。

该约束由 `backend/app/normalize/ids.py` 的 `probe_resource_id`
强制（含冒号即抛 `InvalidResourceId`），并有单测覆盖。
