### 2. GPU 直通模式下显存口径（最关键的一问）

答复确认当前为 **GPU 直通**（非 MDEV/vGPU 切分），并说明
「`GpuMemoryUtilization` 不应直接写成'已用显存字节数'，需要精确显存占用量时，
应结合访客侧 `nvidia-smi`/NVML 数据，并确认单位及统计口径」。

这正是我们要问的：**在直通模式下，如何做跨层比对？**

- 平台侧的 `GpuMemoryUtilization`（卡级使用率，namespace `ZStack/Host`）
  与**虚拟机内 `nvidia-smi` 的显存读数**，是不是同一口径、可以逐点对比？
- 直通模式下虚拟机内 `nvidia-smi` 看到的是**整卡 24576 MiB**，
  还是**按配额切分后分给该虚拟机的那一部分**？
- 若是整卡：是否意味着**无法从访客视角区分"本虚拟机占了多少"与"同宿主其他负载占了多少"**？
  如果是，我们会把"GPU 归因"降级为"宿主卡级压力 + 本机业务表现"的联合判断 ——
  这一点对我们很关键，因为它决定我们能否实现赛题「创新性」维度点名的 **GPU 归因**能力
  （区分"自己超配"与"邻居干扰"）。若平台侧还有别的途径能拿到按虚拟机维度的 GPU 占用
  （例如 vGPU 统计、容器/进程级 GPU 指标），请一并告知。

### 3. 读不到数据要能和「数值为 0」区分开

`GpuUtilization` / `GpuMemoryUtilization` 在**无采样**时（虚拟机未跑负载、
指标未上报、时间点无数据）会怎么返回？

- 返回 `0`？
- 返回 `null` / 空序列？
- 还是省略该时间点？

这一条看着琐碎，但对我们是**正确性问题**：把「读不到」当成「占用 0%」，
在诊断上会被当成一个**好消息**（"显存很空闲"），从而得出完全错误的结论。
所以如果接口层面无法区分，请告知，我们会在适配层用「探测失败」显式表达。

## 五、此前遗漏的 3 项采集侧问题（第一轮未覆盖）

### 5.1 AI 工作负载日志规范（路径 + 格式）

我们计划采集推理服务与 Agent 的日志。若命题方对**日志路径、格式或轮转方式**
有约定或建议，我们据此采集可保证通用性；若无约定，我们将按内置 Agent 接入规范
采集并**在文档中声明所支持的格式**。

### 5.2 探针如何获得 ZSvirt 虚拟机标识（`vmId`）

这是**当前最关键的阻塞点之一**。虚拟机内的探针需要知道「我在哪台 ZSvirt VM 里」，
才能把容器 / 进程 / Agent 信号挂到平台的 VM 对象上。

- 是否支持通过 **cloud-init** 或平台侧元数据服务注入 VM UUID？
- 平台是否有**可被虚拟机读取的元数据端点**（类似 `169.254.169.254`）？
- 虚拟机内是否可读到 `/sys/class/dmi/id/product_uuid` 且其值与平台 UUID 一致？

### 5.3 容器事件采集的权限（`/var/run/docker.sock`）

虚拟机内需要读取容器运行时信息才能采集容器 OOM / 重启事件。

- 测试环境是否允许在虚拟机内挂载 `/var/run/docker.sock`（或 `/run/containerd/containerd.sock`）？
- 是否有推荐的容器运行时（Docker / containerd / Podman）？
- 若上述挂载受限，我们退化为 **cgroup + `/proc`** 采集，但会**丢失 OOM / 重启类关键事件**，
  想先确认限制是否存在。
