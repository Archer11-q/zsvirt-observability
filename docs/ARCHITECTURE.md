## 1. 背景与目标

项目基于上海开源软件应用创新大赛「智算云赛道」ZSvirt 命题：以 **ZSvirt 虚拟机为边界**、以 **AI 工作负载为对象**、以 **事件关联为核心**，建立

```
宿主机 → GPU / vGPU → VM → 容器 / 进程 → AI 服务 / Agent / Task
```

之间的可追溯关系，并完成指标 / 日志 / 事件的采集、告警、跨层关联、根因候选、影响范围与诊断建议。

赛题硬性要求：可运行原型、VM 内探针 / 采集组件、至少一种容器化 AI 工作负载、三类故障场景、可复现材料、3–5 分钟真实环境演示。

### 1.1 成员的职责划分（本项目不只有 B）

| 成员 | 范围 | 与 B 的关系 |
|---|---|---|
| 成员 A | VM 内探针 / 采集（指标、日志、事件采集与上报） | A → B：数据输入方 |
| **成员 B** | **后端平台、数据接入、资源关联、告警、根因诊断、对外 API** | 本文档主体 |
| 成员 C | 前端 / 可视化展示 | B → C：API 消费方 |

### 2.1 由该拓扑直接导出的设计约束

1. **B 不直接采集 GPU 硬件指标。** 本机 WSL 内不存在 `/dev/nvidia*` 设备，`nvidia-smi` 无法给出被管理主机的真实 GPU 状态。GPU / vGPU 维度的数据必须来自 **ZSvirt API** 或 **A 在 VM 内采集并上报**，B 只做接收、标准化与关联。【提案】
2. **B 必须容忍远程依赖不可用。** ZSvirt 集群网络抖动、API 限流、探针断线属于常态，而非异常。
3. **本机当前无 Docker**（Docker Desktop 未对 Ubuntu 发行版开启集成）。【待确认】容器化部署是否为本阶段必需。

## 3. 分层与模块边界

设计原则：**按变化速率分层**，把"随外部系统变化"的部分（适配器）与"系统自身业务"的部分（关联 / 诊断）隔离开。

```
┌──────────────────────────────────────────────────────────────────┐
│  L5  对外契约层   Query API (给 C)                                │
│      拓扑 / 工作负载 / 事件 / 告警 / 诊断 / 健康                    │
├──────────────────────────────────────────────────────────────────┤
│  L4  诊断与告警   Diagnosis Engine │ Alert Engine                 │
│      规则 + 证据链，跨层关联，纯函数、可单测                        │
├──────────────────────────────────────────────────────────────────┤
│  L3  资源图       Resource Graph Store  (Host/GPU/VM/Ctr/Proc/…)  │
│      关系维护 + 影响范围传播                                        │
├──────────────────────────────────────────────────────────────────┤
│  L2  事件存储     Event Store (不可变观测记录)                     │
├──────────────────────────────────────────────────────────────────┤
│  L1  接入与适配                                                   │
│      Ingest Adapter (接收 A) │ ZSvirt Adapter (拉取平台) │ 标准化器 │
└──────────────────────────────────────────────────────────────────┘
```

### 3.1 模块职责与"不做什么"

| 模块 | 负责 | 明确不做 |
|---|---|---|
| `ingest` 接入适配器 | 接收 A 的上报，鉴权、限流、Schema 校验、拒绝并隔离脏数据、写入原始层 | 不改变 A 的采集语义；不替 A 决定探针实现 |
| `zsvirt-adapter` 平台适配层 | 封装 ZSvirt API / SDK，周期同步宿主机 / GPU / vGPU / VM 清单与平台事件 | 不把 ZSvirt SDK 类型泄漏到 L4/L5；不让前端感知 SDK 细节 |
| `normalizer` 标准化器 | 把两路来源映射为统一资源与事件模型，解析 ID 归属 | 不编造缺失的字段（缺失即 `null` + 标记） |
| `resource-graph` 资源图 | 维护资源节点与父子 / 归属关系、影响范围传播、拓扑查询 | 不自行编造不存在的资源关系 |
| `event-store` 事件存储 | 不可变事件记录、时间索引、按资源 / 时间 / 类型检索 | 不承担告警状态机职责 |
| `alert-engine` 告警引擎 | 阈值 / 分级 / 聚合 / 去重 / 静默；状态机 `firing → acked → resolved` | 不把单场景硬编码称为"通用能力" |
| `diagnosis-engine` 诊断引擎 | 跨层事件关联 → 根因候选 + 置信分 + 证据列表 + 影响范围 + 处置建议 | 不输出无法解释来源的黑盒结论；不散落在 Controller |
| `api` 对外契约层 | 稳定、版本化、可诊断错误的 REST 接口 | 不暴露数据库内部结构；不要求 C 直连数据库 |

### 3.2 分层依赖方向（不可反转）

```
L5 → L4 → L3 → L2 → L1
```

- 上层可依赖下层，**下层不得依赖上层**。
- `diagnosis-engine` 不得直接调用 HTTP 或 SQL；它接收**已装配好的上下文对象**，返回诊断结果 —— 这保证它可以脱离数据库被单元测试。
- 所有外部系统（ZSvirt、A 的探针）只允许出现在 L1。

## 4. 数据流

### 4.1 两路输入（关键设计）

| 路径 | 方向 | 内容 | 覆盖的资源维度 |
|---|---|---|---|
| **Pull** | B → ZSvirt API | 周期同步平台清单与平台事件 | 宿主机、GPU / vGPU、VM |
| **Push** | A 探针 → B | 上报指标 / 日志 / 事件 | VM 内：容器、进程、AI 服务 / Agent / Task |

**两条链路通过 `vm` 资源汇合。** VM 是由 ZSvirt 权威定义的资源，探针在 VM 内部运行，因此：

- VM 的 ID 归属：**ZSvirt**（Pull 路径权威）。
- 容器 / 进程 / AI 服务 / Agent 的 ID 归属：**探针**（Push 路径权威），因为 ZSvirt 看不到 VM 内部。
- 关联动作：探针上报时携带 `vmId`（ZSvirt UUID），B 用它把 Push 数据挂到 Pull 建立的 VM 节点下。

> 这是本项目**最核心的一条关联假设**，也是与成员 A 最需要冻结的契约点。见 `API_CONTRACT.md` §A→B。

### 4.2 端到端流程

```
[ZSvirt 集群]                         [VM 内 A 探针]
      │ (1) 周期拉取                        │ (2) 上报 metric/log/event
      ▼                                     ▼
┌──────────────────┐                ┌──────────────────┐
│ zsvirt-adapter   │                │ ingest-adapter   │
└────────┬─────────┘                └────────┬─────────┘
         │                                    │
         └──────────────┬─────────────────────┘
                        ▼
                 ┌─────────────┐
                 │ normalizer  │  统一 ID / 时间语义 / 严重级别
                 └──────┬──────┘
            ┌───────────┴───────────┐
            ▼                       ▼
    ┌───────────────┐       ┌───────────────┐
    │ resource-graph│       │  event-store  │
    └───────┬───────┘       └───────┬───────┘
            └───────────┬───────────┘
                        ▼
                 ┌─────────────┐
                 │alert-engine │  阈值 / 聚合 / 去重 / 静默
                 └──────┬──────┘
                        ▼
                 ┌─────────────────┐
                 │diagnosis-engine │  跨层关联 → 根因候选 + 证据
                 └────────┬────────┘
                          ▼
                    ┌───────────┐
                    │  Query API│ ──→ 成员 C
                    └───────────┘
```

### 4.3 时间语义（【待确认】）

- 事件必须同时记录两个时间：`occurredAt`（事件实际发生时间，由产生方给出）与 `receivedAt`（B 接收到的时间）。
- 跨层关联以 `occurredAt` 为基准，并允许一个**关联容差窗口**（【待确认】，候选值 `±30s`）。
- 时钟漂移风险：本机、ZSvirt 宿主机、各 VM 之间存在时钟偏差。**诊断结论必须对时间窗口敏感，不能假设时钟一致。**

## 5. 诊断链路（概要）

完整设计见 [`backend/DIAGNOSIS_DESIGN.md`](backend/DIAGNOSIS_DESIGN.md)。

链路五步：

1. **触发** —— 由告警或指定时间窗触发一次诊断运行。
2. **汇聚** —— 以受影响资源为锚点，取其上下游资源，拉取窗口内的全部证据（事件 + 指标观测 + 告警）。
3. **关联** —— 对证据做跨层归并，形成候选根因集合。
4. **评估** —— 对每个候选计算**可解释的置信分**（规则加权，非统计学概率）。
5. **输出** —— 根因候选 + 置信分 + 证据列表 + 影响范围 + 处置建议。

**红线**：规则与阈值必须是**声明式数据**，不得为每个故障场景写一次性分支判断。场景只提供规则数据，不提供代码路径。

## 6. 错误处理与降级

| 失败点 | 处理策略 |
|---|---|
| 上报数据 Schema 校验失败 | 拒收并落入隔离区（quarantine），记录原因；**不得静默丢弃** |
| ZSvirt API 不可达 / 限流 | 退避重试 + 熔断；保留上一次成功快照并标记 `dataStaleness`；`/api/health` 暴露降级状态 |
| 探针断线 | 不删除资源节点，标记 `lastSeenAt` 并让健康度降级，避免拓扑抖动 |
| 资源引用不存在（孤儿事件） | 挂到 `unresolved` 占位节点并计数，暴露为健康指标，而非报错丢弃 |
| 诊断引擎无匹配规则 | 返回 `rootCause = UNKNOWN` + 已收集证据 + `confidence = 0`；**绝不编造根因** |
| 任何未预期内部错误 | 统一错误响应（见 `API_CONTRACT.md` §错误模型），带 `traceId`，**禁止裸奔 500** |

## 7.1 设计优先级（依据赛题评分标准）

赛题《【智算云赛道】ZSvirt 赛题》的评审维度权重，**直接决定工程投入的取舍**：

| 评分维度 | 权重 | 本项目的对应设计 |
|---|---|---|
| **可观测与诊断能力** | **25%** | `backend/DIAGNOSIS_DESIGN.md`：规则 + 证据链 + 可复算置信分 |
| **数据与关联模型质量** | **20%** | `DATA_MODEL.md`：统一的资源层级与 ID 语义；L3 资源图 |
| 任务定义与通用性 | 15% | 覆盖容器 / 模型服务 / Agent 多类对象；与 ZSvirt 集成边界清晰 |
| 稳定性与可复现性 | 15% | 最小依赖（ADR-0003）+ 完整 `DEPLOYMENT.md` + **模拟降级模式** |

## 7.2 敏感信息保护（赛题明文要求）

赛题实现约束原文：

> 涉及容器、Agent 或业务日志时，须实现**基本的敏感信息保护措施**，例如脱敏、字段过滤或访问控制说明。

**设计要求**（详细方案见 `SENSITIVE_DATA.md`）：

| 措施 | 落点 |
|---|---|
| 字段过滤 | `normalize` 模块：日志类事件入库前按规则丢弃敏感字段（环境变量、token、凭据、连接串） |
| 脱敏 | 对保留字段做掩码（如 `Authorization`、`*_PASSWORD`、身份标识） |
| 访问控制说明 | `DEPLOYMENT.md` + README 声明认证与权限边界 |
| 原始载荷 | `Event.raw` 保留原始上报，**但必须先过脱敏管道再落库**；若无法安全脱敏，则丢弃并在事件中标记 |

**红线**：不得把包含未脱敏凭据的原始载荷落库或输出到 API。

## 7.3 模拟 / 降级模式（赛题明文要求）

赛题实现约束原文：

> 作品需支持**模拟数据或最小化降级模式**，以便在缺少特定 GPU 硬件时复现实验流程。

| 项 | 设计要求 |
|---|---|
| 触发 | 配置项切换（如 `GPU_PROVIDER=simulated`）；或在真实渠道不可用时自动降级 |
| 覆盖范围 | GPU/vGPU 指标；可选扩展为整套场景数据回放 |
| **可识别性** | `/api/health` 的 `gpuProvider.mode` 必须暴露当前渠道 |
| **诚实性红线** | 模拟数据**不得伪装成真实采集数据**进入证据链而不加标记 |
| 用途 | ① 开发机无 GPU 时开发与自测；② 演示兜底；③ 评委复现 |
