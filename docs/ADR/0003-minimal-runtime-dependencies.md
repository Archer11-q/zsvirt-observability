## 范围扩展（2026-09-17）

赛题《【智算云赛道】ZSvirt 赛题》实现约束原文：

> **可使用** OpenTelemetry、Prometheus、Grafana、eBPF、Fluent Bit、Jaeger 等开源组件，
> 也可在此基础上完成创新；**不得将不可验证的闭源服务作为核心能力**。

**注意措辞：是「可使用」（允许），不是「必须使用」。** 项目成员决策**不引入**这四个可观测组件：

| 组件 | 为什么这里不用 |
|---|---|
| Prometheus | 指标存储与查询用 PostgreSQL 足以覆盖当前规模（单机原型 + 3 个故障场景） |
| Grafana | 成员 C 已提出完整自建前端方案（React 18 + Vite + Ant Design 5 + ECharts 5），引入 Grafana 会造成两套可视化并存 |
| OpenTelemetry Collector | 属额外中间件；A 的探针可直接 HTTP 上报，B 侧 `ingest` 已有完整契约 |
| Jaeger | 分布式追踪非赛题必需（赛题说"至少覆盖指标、日志、事件三类信号中的**两类**"，鼓励但不要求追踪） |

**决策依据**：赛题「稳定性与可复现性」为独立评分项（**权重 15%**），要求
「部署流程是否清晰；同一场景下结果是否稳定；**最小化环境能否复现**」。
组件越少，评委从零复现的难度越低。

**扩展后的边界**：

- **不引入**：消息队列（Kafka / NATS / RabbitMQ）、搜索引擎（Elasticsearch）、
  独立缓存（Redis）、分布式追踪后端（Jaeger / OTel Collector）、
  指标与可视化栈（Prometheus / Grafana）。
- **允许引入**（已有决策）：PostgreSQL、嵌入式 SQLite（**仅在探针侧**，属成员 A 的实现选择）。
- **例外通道**：若后续出现 PostgreSQL 确实无法覆盖的具体证据（例如事件表规模压垮查询性能），
  需新增 ADR 并重新评审 —— **不得以"赛题允许"为理由直接引入**。

## 背景

后端平台的常规做法会引入若干基础设施组件：

| 组件 | 常规用途 |
|---|---|
| Kafka / NATS / RabbitMQ | 采集数据缓冲、削峰、解耦 |
| Elasticsearch | 日志全文检索 |
| Redis | 缓存、告警聚合状态 |
| Jaeger / OTel Collector | 分布式追踪后端 |

本项目有三个具体约束：

1. 团队控制协议明确规定：**新增 Kafka、Elasticsearch、Jaeger、OTel Collector、eBPF 等重大组件必须停下来让团队确认**。
2. 赛题要求的**「可复现」**是评分项：组件越多，评委从零复现的难度越高。
3. 当前规模（单机原型、三类故障场景、3–5 分钟演示）**远未触及**这些组件解决的问题所在。

## 决策

**不引入**消息队列、搜索引擎、分布式追踪后端与独立缓存组件。

具体落地：

- A → B 的数据接入采用 **HTTP 批量上报**（`POST /api/v1/ingest/batch`），不使用消息队列。
- 日志检索与事件查询全部走 **PostgreSQL**（结构化查询 + 索引）。
- 告警聚合与去重状态存储在 **PostgreSQL**，不引入 Redis。
- 诊断引擎是**进程内纯函数模块**，无外部依赖。

## 备选方案

| 方案 | 优点 | 缺点 | 为何未选 |
|---|---|---|---|
| 最小依赖（HTTP + PostgreSQL） | 复现门槛最低；组件最少；符合协议约束 | 高吞吐场景需自行实现缓冲与背压 | **选定** |
| 引入 Kafka 做接入缓冲 | 削峰能力强；探针与后端解耦 | 属重大组件需团队确认；演示环境复杂度显著上升；当前吞吐量根本用不到 | 收益不匹配成本 |
| 引入 Redis 做告警聚合 | 聚合与去重状态读写快 | 又一个必须运维的组件；PostgreSQL 完全可以承担当前量级 | 收益不匹配成本 |
| 引入 Elasticsearch 做日志检索 | 全文检索能力强 | 资源占用大（JVM + 堆内存）；复现门槛高；当前只需按资源/时间/类型过滤 | 收益不匹配成本 |

## 后果

### 正面

- `DEPLOYMENT.md` 的搭建步骤只需 Python + PostgreSQL 两项，评委可复现性高。
- 排障面小：出问题时只需排查应用与数据库。
- 符合团队控制协议的依赖纪律。

### 负面 / 代价

- **需要自行处理背压**：探针上报速率超过处理能力时，B 必须有明确的策略（限流 + 拒收 + 明确错误码），不能无限缓冲导致 OOM。
- **PostgreSQL 承担全部查询负载**：事件表会持续增长，需要索引设计与保留策略（【待确认】）。
- 未来若规模真的增长，接入层需要改造——但 `ingest` 适配器是唯一耦合点，改造范围可控。

### 需要后续跟进

1. 定义上报限流策略与 `429 RATE_LIMITED` 的触发条件（`API_CONTRACT.md` §2.3 已预留错误码）。
2. 定义事件表的索引方案与数据保留策略。
3. 明确背压时的拒收行为：**必须给出明确错误，不得静默丢弃**。

## 回滚方案

若未来必须引入消息队列：新增 ADR 标记本决策 `Superseded`，并在 `ingest` 适配器后插入队列——由于 L1 是唯一外部耦合层（`ARCHITECTURE.md` §3.2），L2 以上模块**不应需要修改**。若改动波及 L2 以上，说明分层被破坏，需先重构。

当前阶段回滚成本为零（尚未实现）。

## 验证方式

- 从干净环境按 `DEPLOYMENT.md` 启动，`apt`/`pip` 安装列表里不出现任何消息队列或搜索引擎。
- 压测上报端点，确认在超阈值时返回 `429` 且服务不崩溃、不 OOM。
- `/api/health` 的 `components` 中只有 `database` / `zsvirt` / `ingest` 三项上游。
