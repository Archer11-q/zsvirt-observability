## 背景

项目需要交付一个可运行的后端平台：接收 VM 内探针上报的指标/日志/事件，接入 ZSvirt 平台资源清单，维护跨层资源关系，产出告警与可解释诊断，并通过稳定 API 提供给前端。

技术选型必须在**写第一行业务代码之前**固定，因为后续所有契约（接口形态、部署方式、依赖清单）都建立在它之上。

关键约束：

- 赛题要求「可复现」：环境搭建步骤必须简单、明确。
- 团队成员在 Windows 上用 WSL2 Ubuntu 开发，不能依赖重型企业级工具链。
- 数据模型会频繁演进（资源层级、事件字段仍在确认中），需要低摩擦的迭代能力。
- 运行时依赖策略已确定为**最小化**。

## 决策

后端采用：

| 层 | 选型 |
|---|---|
| 语言 | **Python 3.12+** |
| Web 框架 | **FastAPI** |
| 数据库 | **PostgreSQL** |
| ORM | **SQLAlchemy** |

## 备选方案

| 方案 | 优点 | 缺点 | 为何未选 |
|---|---|---|---|
| Python + FastAPI | 迭代最快；Pydantic 原生支持 Schema 校验（正好用于 A→B 上报契约）；生态成熟；团队环境已具备 | 单线程性能低于 Go；需要 venv 管理 | **选定** |
| Go + Gin/Echo | 单二进制部署；并发采集接入强；内存占用低 | 类型系统对频繁演进的 Schema 摩擦大；WSL 当前未安装 Go 工具链；开发速度慢于 Python | 迭代速度是当前主要矛盾 |
| Java + Spring Boot | 生态完善；企业级能力齐全 | WSL 的 JAVA_HOME/maven 配置已损坏需先修；启动重；对这种规模的原型过重 | 收益不匹配成本 |
| C++ / CMake | 与远程仓库现有 `.gitignore`（C/C++ 模板）一致 | Web 服务开发与迭代成本极高；无成熟快速开发框架；不适合赛题节奏 | 仅当团队另有全局约束才考虑 |

> 备注：远程仓库的 `.gitignore` 是 C/C++ + CMake + vcpkg 模板，与本次决策不一致。该文件需在 A/C 同意后重写为 Python 版本（见 `TECH-BASELINE.md` R6）。

## 后果

### 正面

- A→B 上报契约可以直接用 Pydantic 模型表达，Schema 校验与契约文档可保持同步。
- 无需引入额外中间件即可完成全部后端能力，符合最小依赖策略。
- 熟悉的语言缩短从设计到可运行原型的距离。

### 负面 / 代价

- 需要显式管理 Python 版本：勘测机为 3.14.4，基线锁定 3.12，存在版本差（已在 `TECH-BASELINE.md` §2.1 记录）。
- 勘测机 `pip3` 缺失，需补装。
- 高并发采集接入场景下需要评估 uvicorn worker 数量与连接池配置。

### 需要后续跟进

1. 解决 Python 3.12 vs 3.14 的版本差。
2. 安装 PostgreSQL。
3. 锁定 `requirements.txt` 精确版本与许可证清单。
4. 重写 `.gitignore`（需 A/C 同意）。

## 回滚方案

本决策影响的是**尚未编写**的代码，因此回滚成本在当前阶段最低。一旦开始实现，回滚代价按已写代码量线性上升。

若需回滚（例如改为 Go）：在 B2 开发开工前重新评审本 ADR，标记为 `Superseded`，并新增 ADR。**已冻结的 API 契约（JSON over HTTP）尽量保持不变**，因为契约与语言实现解耦——这是本项目分层设计的直接收益。

## 验证方式

- `DEPLOYMENT.md` 的搭建步骤在干净 Ubuntu 上实测可跑通。
- MVP 验收闭环（见 `TEST_PLAN.md` §2）全部通过。
- 服务在最小环境（仅 Python + PostgreSQL）中启动，不需要消息队列或搜索引擎。
