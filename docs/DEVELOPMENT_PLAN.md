1. `chain_intermediates` 只处理"证据在锚点**下游**"一个方向 —— 而本项目最常见的

| 子项 | 结果 |
|---|---|
| 规则集 | ✅ 覆盖三类赛题场景 + 平台自监控；规则是**数据**，`assert_rules_are_consistent` 校验所有引用 |
| 求值 | ✅ 事件写入后求值，**与事件同事务**（告警和它的证据一起可见或一起不可见） |
| 聚合去重 | ✅ 按 `aggregationKey` 累加 `count` 与证据，**不新建**告警 |
| 证据绑定 | ✅ `evidenceEventIds` 非空 —— 引擎与数据库 CHECK 双重强制 |
| 分级 | ✅ 取规则与事件中**更严重**的一方，不降级显示 |
| 静默 | ✅ 静默期内只更新证据、不动状态；到期释放时**重新基准化** `lastFiredAt` |
| 恢复 | ✅ 超恢复窗口无新证据 → `resolved` + `resolvedAt`；复发新建告警 |
| 上报响应 | ✅ 带上告警摘要（`created`/`updated`/`skippedSilenced`），探针不必轮询 |

**验收标准对照**：6 条全部满足。

**过程中发现并修正的 5 个缺陷**（详见 `DECISIONS.md` v0.4）：

1. **测试隔离缺口**（影响所有后续任务）：`TRUNCATE` 只挂在 `db_session` 夹具上，
   只请求 `client` 的用例写库后不清理，数据泄漏给后续用例 —— 症状是
   "单独跑通过、一起跑失败"。清理逻辑已抽为 `_truncate_all` 并由两个夹具共用。
2. **`count` 与证据自相矛盾**：新建告警时 `count` 硬编码 1，但一批可能命中多条
   事件（`evidenceEventIds` 有 3 条而 `count=1`）。运维靠 `count` 判断频率。
3. **`lastFiredAt` 用接收时间**：迟到批次会让告警排到列表最前，而它旁边的证据
   时间戳是十分钟前。改为跟随事件的 `occurredAt`。
4. **静默到期被当成"已恢复"**：静默期内没有新证据，是因为**我们没在听**，
   不能推断"问题消失"。释放时把 `lastFiredAt` 重新基准化到释放时刻。
5. **`reconcile_all` 没有 flush**：`reconcile` 用同一 session 发 SELECT，而本项目
   关闭了 autoflush，未 flush 的状态改动对它不可见 —— 刚释放的静默告警会被立刻
   判为已恢复，正是第 4 条要防的行为。

> 教训：第 4、5 两条都是"合理推断在特定时序下变成错误结论"。负向用例必须断言
> **具体状态**，只断言"没有异常"会写出假通过。

| 降级 | ✅ 诊断在**上报事务提交之后**执行，失败逐条记录、不影响告警与上报 |
| 范围 | ✅ 只自动诊断 `error` 以上告警；提示级由用户按需"一键诊断" |

**为什么不放在上报事务里**：一次上报可能瞬间产生十几条告警，每条都
"装配资源图 + 扫时间窗事件"会把探针写入延迟放大到秒级 —— 而探针批量上限是
1 秒 / 1MB，写入变慢会直接反压到采集。数据采集是主流程，根因分析是增值能力，
增值能力不能毁掉主流程（D-089）。

**验收标准对照**：任务 3 的四条全部满足，并额外覆盖"不该做什么"
（提示级不诊断、已恢复/已静默不诊断、重复批次不诊断、失败不改告警）。

**过程中发现并修正的 1 个致命缺陷 + 3 个缺陷**（详见 `DECISIONS.md` v0.6）：

1. 🔴 **`resource_edge` 从不被真实上报填充**（最严重）。`upsert_resource` 写
   `parent_id`，`ensure_edge` 写边表，而**真实上报路径从不调用 `ensure_edge`**。
   于是 `load_graph`（遍历边表）在真实数据上返回一堆孤立节点：拓扑没有连线、
   工作负载找不到链路成员（计数恒为 0、GPU 永远解析不到）、诊断的
   `ancestors` / `descendants` 全为空。
   这个缺口被"所有测试都手工建边"掩盖了很久 ——
   **测试自己造夹具就抓不到这类缺陷，只有端到端路径能**。
2. `Rule.contradicts` 声明了但引擎从未求值：反证规则无法表达，
   「邻居争用 vs 本机超配」这个核心区分做不出来。
3. 指标型规则**永远不可能命中**：证据的 `name` 是事件类型，单个指标名从不可见。
4. 规则集里「邻居争用」匹配 `gpu.neighbor.contention` —— 一个**不存在**的事件类型
   （F-01 的 17 项里没有它）。那让 GPU 归因看起来被覆盖，实际邻居侧永不触发。

**过程中修正 9 个缺陷**（单场景单测全部漏过，只有多场景端到端验证能抓到）：

1. 🔴 **`load_graph` 是无向闭包** —— 从容器向上走到 VM 后会再向下走进兄弟分支，
   两个兄弟容器互相出现在对方的可达范围里。**只有存在第二个兄弟节点时才显现**，
   此前所有测试都只有一条链。
2. 事故聚合判据两次写错：按可达闭包相交会把整条链并成一次事故（三类故障只剩一条
   结论）；按资源相等又把一次事故拆成两条。最终判据是「一方是另一方的**祖先或
   相等** + 时间窗重叠」。
3. 事故锚点取错成员，使事故上方成员的证据被"忽略祖先证据"规则误过滤。
4. 诊断吃到锚点**祖先**上的无关故障证据（容器事故被 vGPU 的 GPU 事件压过）。
5. 逐条告警诊断导致重复结论 —— 改为按事故聚合。
6. 工作负载卡片显示"整条链上最新的一次事故" —— 归并改为按贴近程度排序
   （0=点名该工作负载 / 1=点名其下层资源 / 2=仅从共享基础设施波及）。
7. 场景让三次故障共用同一套工作负载资源且时间戳相同，被合理并成一次事故。
8. `suffix` 算在分支之后，资源 id 变成 `demo-ctr-None` —— 一个**合法** id，
   不会被任何校验拦住，只会让多个场景静默共用资源。已加自检。
9. 增量替换式的选主逻辑难以验证，改为一次性计算排序键。

> 教训：**测试自己造夹具抓不到"夹具是唯一在造这个东西的地方"**。

**过程中发现并修正的 8 个缺陷/阻塞**（详见 `DECISIONS.md` v0.8）：

1. 🔴 **`_infer_parent_kind("process")` 猜成 `vm`**，而 A 的样例里 process 的父是
   **container** —— 拼出不存在的父 id，`upsert_resource` 在同一条 INSERT 里写
   `parent_id`，**外键违约让整批上报 503**。父类型现在从**本批声明的资源**里查，
   不是猜（一个 process 的父可能是容器也可能是 VM，按子类型猜必然错一半）。
   同时 `upsert_resource` 不再把 `parent_id` 指向不存在的资源。
2. 🔴 **`resource.hierarchy` 之外还有一条死规则**：诊断规则集匹配
   `vm.memory.exhausted` —— F-01 的 17 项里**没有这个类型**，规则永不命中。
   改成匹配真实可得的事件（`process.crash` / `process.io_wait.high`）。
3. **`process.io_wait.high` 被采集但无人告警**：A 的收集器已在实现它，
   B 的规则集里没有任何规则引用 —— 数据进来了却没人看。补 `R-PROC-IOWAIT-013`。
4. 🔴 **平台层命名空间桥接缺失**：`zsvirt_resource_id` 在**整个代码库没有调用方**，
   所以探针命名空间（`{kind}:probe:{agentId}:{sourceId}`）与 ZSvirt 命名空间
   （`{kind}:zsvirt:{uuid}`）之间没有任何映射。当前所有平台层资源（host/gpu/vgpu/vm）
   都只能由探针代为上报 —— 真实部署里这是错的。已断言为事实（3 项测试），
   并升级为**关键路径阻塞**。
5. 探针样例不含 `vm`，因此容器无父、图是断开的 —— 这是设计如此（探针不拥有
   VM 的权威），但它是第 4 条的后果，必须被记录而不是被当成"探针漏报"。
6. 我自己的测试有隔离缺陷（自建 `client` 夹具替换掉了 conftest 的清理），
   表现为"OOM 样例的告警泄漏到网络样例"。已加 autouse 清理夹具。
7. 我的脱敏断言过宽（按子串搜 `password`，命中了 kernel log 的自由文本）。
   脱敏针对的是键值，不是自由文本；改为查**键名**并单独查密钥值。
8. 我的命名空间守卫用字符串搜函数名，被**解释该缺口的注释/文档字符串**引信点燃。
   改为匹配**调用**（名字加左括号）—— 散文写名字，代码写调用。
