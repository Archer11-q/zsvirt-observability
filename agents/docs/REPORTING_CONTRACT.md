## 2. 逐条决策

### Q1 — `resourceRef` 引用的资源是否保证同批次或之前出现过？

**决策：主保证 + 兜底。**

- **主保证**：探针侧维护「已确认资源」缓存（`sourceId → 已上报状态`）。事件引用的资源，要么与事件**同批次**上报，要么已在此前批次被 B 接受（响应中 `accepted`）。若事件引用的资源尚未被确认，探针必须把该资源一并放入本批 `resources`，再发事件。
- **兜底**：极端竞态（资源创建后立即产生事件、来不及进入任何批次）允许出现孤儿引用，由 B 的 `unresolved` 占位机制承接（`ARCHITECTURE.md` §6、`BACKEND_DESIGN.md` §4、`ADR-0002` 负向测试均已约定），不丢数据、不报错。

**理由**：既让 B 无需新增占位缓冲（它本就有 `unresolved`），又避免探针为覆盖极端竞态引入复杂的事务一致性，符合最小依赖。

**对 B 的诉求**：上报响应（§3.4）需逐条给出每个 resource 的接受结果，A 据此更新缓存；孤儿事件挂 `unresolved` 后应计数并暴露为健康指标。

### Q2 — 上报是至少一次还是恰好一次？

**决策：至少一次（at-least-once），允许重复投递。**

- `batchId` 用 **ULID**（时间单调有序），断网重试时**复用同一 `batchId`**，不换号。
- 去重由 B 按 `batchId` 幂等完成；A 不自行保证恰好一次。

**理由**：VM 内探针在断网/重试场景下无法廉价实现恰好一次（需分布式事务或去重存储），与「最小依赖」基线冲突；`batchId` 幂等是标准且廉价的替代。

**对 B 的诉求**：幂等去重以 `batchId` 为唯一键；重复批次应返回与首次一致的结果（`200` + 已处理标记），不要因此误判为脏数据。

### Q3 — 探针时间戳来源与时钟同步方式？

**决策：ISO 8601 UTC 毫秒 + NTP，`sentAt` 供 B 算漂移。**

- 所有时间戳采用 **ISO 8601 UTC、毫秒精度、带 `Z`**（遵循 `TECH-BASELINE.md` §3）。
- 时钟基准优先 **NTP**；VM 内无 NTP 时退化为宿主机/VM 时钟，并在启动握手时与 B 做一次时钟偏移采样（可选增强）。
- 每个 batch 携带 `sentAt`，B 用 `receivedAt − sentAt` 计算网络延迟与时钟漂移。

**理由**：跨层关联以 `occurredAt` 为基准，时钟漂移会直接导致漏关联（`ARCHITECTURE.md` §4.3）。`receivedAt` 由 B 记录、`sentAt` 由 A 给出，两者相减即可持续监测漂移。

**对 B 的诉求**：B 在 `ingest` 侧计算 `receivedAt − sentAt` 的偏移，暴露为健康指标；建议漂移告警阈值 **|offset| > 5s**（严于关联容差窗口 ±30s，提前预警）。关联容差窗口维持候选值 **±30s**，A 无异议。

### Q4 — 批量大小上限与上报频率？

**决策：默认 5s 一批，事件实时优先，设硬上限。**

- 正常节奏：**每 5 秒**聚合上报一批（资源清单/心跳）。
- 事件**实时优先**：有新事件时最多缓冲 1 秒即发，不硬等 5s。
- 硬上限（对齐 `DEPLOYMENT.md` §4 的 `INGEST_BATCH_MAX`）：
  - `events ≤ 1000` / 批
  - `resources ≤ 500` / 批
  - 单批 payload ≤ 1MB
- 触发「达上限」或「超时」即发（先到先发）；收到 `429 RATE_LIMITED` 时按指数退避重试。

**理由**：给 B 的限流与批次上限一个明确锚点，同时避免探针积压；1MB 是 HTTP 批量上报的合理边界。

**对 B 的诉求**：明确 `429` 的触发阈值与 `Retry-After` 语义；A 按 `Retry-After`（或默认指数退避）重试，不无脑重放。

### Q5 — 探针如何发现 B 的地址？

**决策：环境变量 + 配置文件，不引入服务发现。**

- 主通道：环境变量 `ZSVIRT_OBS_BACKEND_URL`（默认 `http://<B-host>:8080`，对应 `DEPLOYMENT.md` §5 的 B API 端口）。
- 覆盖通道：本地配置文件（如 `/etc/zsvirt-probe/config.yaml` 或工作目录 `probe.yaml`）。
- 优先级：**环境变量 > 配置文件 > 默认值**。

**理由**：VM 内网络简单，DNS + 固定端口足够；服务发现属多余组件，违背 `ADR-0003` 最小依赖。

### Q6 — 断网期间数据如何处理？

**决策：本地磁盘缓冲 + 断点续传（FIFO），超限丢最旧并计数。**

- 断网时事件与资源增量写入**本地磁盘缓冲**，恢复后按序补传。
- 实现选型：**嵌入式 SQLite**（原子写、崩溃安全）或 append-only JSONL 文件均可，二者均非重大组件，不违背最小依赖。
- 缓冲上限可配置（默认 100MB 或 10000 条事件），**超限丢最旧并计数**（丢弃数随后续批次上报）。
- 补传时复用原 `batchId`，保证 B 幂等去重仍生效。

**理由**：保住「可复现」评分与事件完整性；背压由「上限 + 丢弃计数」显式表达，避免探针无限占用磁盘（呼应 `ADR-0003` 对背压的要求）。

**对 B 的诉求**：对「迟到/乱序」的历史批次按 `occurredAt` 追加写入，不得因 `occurredAt` 早于当前时间而丢弃或告警。

### Q7 — 是否需要鉴权？

**决策：可选共享 token，不引入 mTLS，默认关闭。**

- 支持可选的共享 token：请求头 `Authorization: Bearer <token>`。
- token 仅从环境变量 `ZSVIRT_OBS_PROBE_TOKEN` 注入，**绝不写入仓库、配置文件或提交**（遵守 `CONTRIBUTING.md` §8 红线）。
- 不引入 mTLS（证书签发与轮换复杂，违背最小依赖）。
- **默认关闭**；是否强制由部署侧（B）决定。

**理由**：MVP 阶段留出安全边界但不过度工程；token 从环境变量注入即满足「凭据不进仓库」纪律。

**对 B 的诉求**：若 B 开启强制鉴权，探针未带/带错 token 时应返回 `401 UNAUTHENTICATED`（错误码已预留）；A 收到 `401` 明确报错并停止重试（不把鉴权失败当网络故障无限重放）。

## 3. 关联确认：探针侧 `sourceId` 生成规则（`DATA_MODEL.md` R5 / `ADR-0002` 阻塞点）

Q1 的 `resourceRef` 依赖稳定的 `sourceId`，这里一并给出 A 的初步提案（**需 B 确认拼装方式**）：

| kind | `sourceId` 建议规则 | 稳定性来源 |
|---|---|---|
| `container` | 容器 ID 前 12 位（或容器名，若唯一） | 容器生命周期内不变 |
| `process` | `starttime + pid`（取自 `/proc/<pid>/stat`） | 避免 pid 复用冲突 |
| `ai_service` | `服务名 + 监听端口` | 服务实例稳定标识 |
| `agent` | 探针分配的 ULID | 全局唯一 |
| `task` | 探针分配的 ULID | 全局唯一 |

统一要求：**同一 `agentId` 内唯一、生命周期内不变**。`agentId` 建议 `probe-<vm-uuid 前 8 位>`，与契约示例 `probe-<vm-uuid>-01` 对齐。

## 4. 探针上报实现要点（备忘，非本契约内容）

- 传输：HTTP POST `POST /api/v1/ingest/batch`，`Content-Type: application/json`。
- 必填：`agentId`、`vmId`（ZSvirt UUID，Push 挂到 Pull 的唯一锚点）、`agentVersion`、`batchId`、`sentAt`。
- 字段纪律：来源系统没给的字段一律不编造，缺失留 `null`（对齐 `DATA_MODEL.md` §1）。
- 部分接受：被拒条目必须能映射回本批 index，便于定位探针 bug。

## 5. 需要 B 侧配合的清单

1. §3.4 响应逐条返回 resource 接受结果（Q1）。
2. `batchId` 幂等去重，重复批次返回一致结果（Q2）。
3. `ingest` 侧计算并暴露时钟漂移，建议阈值 5s（Q3）。
4. 明确 `429` 触发阈值与 `Retry-After`（Q4）。
5. 历史批次按 `occurredAt` 追加，不因迟到丢弃（Q6）。
6. 强制鉴权时返回 `401 UNAUTHENTICATED`（Q7）。
